# Module Sizing Guide

> 03-2 前端详细设计的模块分级与文档产出矩阵。用于控制文档数量和阅读成本，避免所有模块都默认产出一整套重文档。

## 目标

- 让文档产出与模块复杂度匹配
- 把公共规则上移到阶段级文档，减少模块级重复
- 让人和 AI Agent 都能用更低的阅读成本进入模块设计

## 模块分级

### 小模块

典型特征：
- 单页面或单流程改动
- 组件数量少，职责简单
- 状态流转简单
- 不需要复杂组件协作边界

默认产出：
- `design-plan.md`
- `work-item-breakdown.md`

按需补充：
- `page-design.md`

通常不需要：
- `component-design.md`

### 中模块

典型特征：
- 有清晰的页面主流程
- 有 1-2 组关键交互状态
- 页面设计和任务拆解都需要沉淀
- 组件边界存在，但不复杂到需要单独展开整篇组件文档

默认产出：
- `design-plan.md`
- `page-design.md`
- `work-item-breakdown.md`

按需补充：
- `component-design.md`

### 大模块

典型特征：
- 工作台或复合型页面
- 多个子区域协同
- 状态机复杂
- 组件职责和状态归属复杂
- 需要多 Agent 或多人并行协作

默认产出：
- `design-plan.md`
- `page-design.md`
- `component-design.md`
- `work-item-breakdown.md`

## 文档裁剪原则

- 公共规则写在 `CLAUDE.md`、`integrations/` 或其他阶段级文档，不在每个模块里重复解释。
- 模块文档只写“本模块特有”的范围、流程、状态、边界、风险和验收。
- 若某部分内容没有形成独立决策价值，就不要单独拆成一篇文档。

## 各文档适用场景

### `design-plan.md`

适用于所有模块。

应重点保留：
- 模块范围
- 关键约束
- 决策记录
- 风险与待确认项
- 文档产出选择

不应膨胀为：
- 背景知识大全
- 所有公共规则的复制版

### `page-design.md`

当模块存在明确页面主流程、状态切换、布局区域或 API 触点时使用。

适合承载：
- 路由与主视图
- 主流程与失败回路
- 页面状态
- API 交互触点

### `component-design.md`

只有在以下情况成立时才建议单独产出：
- 组件职责边界不清
- 状态归属复杂
- 存在跨区域交互
- 需要并行开发或复杂 handoff

否则可把关键组件说明直接写进 `page-design.md`。

### `work-item-breakdown.md`

适用于需要把设计结果同步到 PingCode 的模块。

应重点保留：
- 用户故事到能力闭环任务的映射
- 依赖关系
- 验收口径

不应演变为：
- 长期任务台账
- 细碎实现步骤清单

## 推荐判断顺序

1. 先判断模块是小 / 中 / 大
2. 先确定最小必需文档集合
3. 只有在信息确实会丢失时，才新增下一层文档
4. 若模块后续复杂度上升，再从小集合升级到完整集合
