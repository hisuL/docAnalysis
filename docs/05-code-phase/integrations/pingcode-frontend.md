# PingCode Frontend Guide

> 面向前端开发的 PingCode 工作流。PingCode 负责“任务从哪里来、如何拆分、如何同步状态”，不替代设计文档。

## 什么时候进入 PingCode
- 需要领取新的前端任务或 BUG 时
- 需要拆分用户故事、同步进展、回写状态时
- 需要确认当前执行优先级或验收边界时

## 必须使用的入口
- 优先使用本地 `skills/pingcode-front/SKILL.md`
- 只有在本地 skill 能力不覆盖时，才退回 PingCode 前端页面操作

## 任务筛选规则
只关注以下任一条件命中的工作项：
- 负责人是 `赵帅更`
- 任务类型是“前端”
- 标题包含“前端”

如果同时不满足以上条件，不默认接单，先核对是否确属当前前端范围。

## 标准流程
1. 先进入 PingCode 查任务、BUG 或当前已领取工作项
2. 读取工作项标题、描述、验收标准、优先级、复现信息、评论区补充说明
3. 若任务边界不清，再对照 `docs/03-2-frontend-design/` 和 `docs/03-1-backend-design/`
4. 若是用户故事或过粗任务，先拆分为适合编码推进的前端工作项
5. 如有 `frontend/PLANS.md`，可把当前正在执行的工作项同步为执行快照
6. 开发完成后，把可验证的进展、状态或备注同步回 PingCode

## 用户故事拆分规则
- 用户故事必须拆分工作项，不能直接作为前端编码待办
- 拆分后的工作项继续指派给 `赵帅更`
- 任务类别统一设置为“前端开发”
- 标题统一加前缀 `[前端]`
- 工作项优先保持“能力闭环”粒度，不按实现动作穷举拆成大量小任务
- 子任务要能直接落到完整功能块、联调闭环、测试闭环或缺陷修复，不要只写“开发/联调/测试”这种空泛标题

## 与设计文档的关系
- PingCode 决定当前做什么、优先级是什么、验收看什么
- `docs/03-2-frontend-design/` 决定页面、组件、交互和状态设计
- `docs/03-1-backend-design/` 决定接口、错误码、状态机和契约
- `docs/05-code-phase/front/` 决定实现约束和前端落地方式
- `frontend/PLANS.md` 如存在，只承担当前执行快照，不替代 PingCode

## 不该怎么做
- 不把 PingCode 当作唯一设计依据
- 不因为任务字段简略就跳过设计文档
- 不把非前端范围的任务默认拉进当前开发流
- 不在未拆分用户故事的情况下直接开始编码
- 不把 Agent 的内部执行步骤全部外化成 PingCode 子任务
- 不同步未经验证的“已完成”“已联调通过”“已测试通过”结论

## 发现问题时怎么做
1. 记录冲突点或缺失点
2. 标明影响范围、当前理解和阻塞点
3. 必要时同步到 `docs/05-code-phase/front/CHANGELOG.md`
4. 在任务未澄清前，不擅自重定义业务规则
