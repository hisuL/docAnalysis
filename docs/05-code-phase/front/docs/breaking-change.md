# Frontend Breaking Change Guide

> 这是一个升级处理手册，不是前端默认起手文档。只有在接口、状态、交互语义出现不兼容变化时，才进入本流程。

## 什么时候算 Breaking Change
以下情况默认视为 breaking change：
- 已有接口字段被删除
- 已有字段类型变化或语义变化
- 枚举值、状态机、错误码变化
- 接口路径、请求方法、鉴权方式变化
- 返回结构包裹层变化
- 流式协议格式变化
- 页面交互语义变化，导致现有组件职责或状态流转失效
- YAPI Mock 与正式契约明显不一致，导致前端判断失真

## 处理流程
1. 不静默兼容，不猜测后端或产品意图
2. 先记录变更点和影响范围
3. 对照 `docs/03-1-backend-design/` 与 `docs/03-2-frontend-design/` 确认权威定义
4. 标明受影响的页面、组件、hooks、API client 和测试
5. 若设计文档已变化，先同步文档，再修改代码
6. 若风险较高或影响范围不清，暂停继续批量实现，等待确认

## 为什么单独保留本文档
- 它只在高风险场景触发，不适合塞进日常 `frontend/CLAUDE.md`
- 它需要强调“停下来、记录影响、升级确认”，和普通开发流程不同
- `.claude/rules/frontend-breaking-change.md` 可以在改动前端代码时提供一个稳定的自动提醒入口

## 冲突判断优先级
- 业务语义、接口字段、状态机、错误码：以后端 `docs/03-1-backend-design/` 与前端 `docs/03-2-frontend-design/` 的设计结论为准
- 前端实现细节、请求层组织、目录落点：以前端代码和 `docs/05-code-phase/front/docs/` 为准
- YAPI 或其他集成平台的展示内容与设计冲突时，不以平台展示直接覆盖设计文档

## 记录要求
- 记录到 `docs/05-code-phase/front/CHANGELOG.md`
- 至少包含：变更点、时间、影响范围、当前风险、建议动作
- 若是联调阶段发现的问题，补充关联接口和是否涉及 Mock
